## 1. 上一版 P0/P1 逐条复核

复核方式：直接读当前代码定位，不依赖上一版报告的描述。

### P0-1 EXIF 自动旋转缺失（**已于评审当日修复**，见 §6；影响面比上一版描述更大）

`ImageProcessor.ts:70-73`，`sharp()` 之后直接进 resize，**整条管线没有 `.rotate()`**：

```ts
let pipeline = sharp(input.path, { failOnError: false, limitInputPixels: 268402689 });
// ↑ 没有 .rotate()，EXIF Orientation 不会烧进像素
```

而默认 `removeMetadata ?? true`（`:86`、`:378`、`:385`、`:396`），smart 模式强制 `true`（`:365-371`）
→ **Orientation 标记被剥掉、像素没旋转**。

**实测（`test-temp/review/verify-2026-09-23.txt`，构造 200×100 + Orientation=6 的竖拍照片）：**

```
== [1] EXIF 方向：FileScanner 的 dimensions 与视觉尺寸 ==
  文件元数据        : 200x100 orientation=6
  FileScanner 记录  : 200x100  <<< 未考虑 EXIF
  「朝上」的真实尺寸: 100x200  <<< 竖图

== [2] process() 当前管线 vs 加 .rotate() （模拟 resize longEdge=100）==
  applyResize 依据 dimensions 判定 landscape=true → resize({"width":100})
  当前管线输出      : 100x50  orientation=undefined   <<< 躺倒的横图，EXIF 已丢，无从还原
  加 .rotate() 输出 : 100x200 orientation=undefined   <<< 像素已定向
```

**本次新增的两个连带影响（上一版报告没提）：**

1. **连带 `resize` 选错轴。** `FileScanner.processFile:90-93` 用的是裸 `sharp(filePath).metadata()`，
   读到的是**未旋转的像素尺寸**，直接作为 `ImageFile.dimensions` 落库。
   而 `applyResize` 的 `longEdge` / `shortEdge` 靠 `width >= height` 判断横竖（`ImageProcessor.ts:301-315`）：
   竖拍照片会被判成横图，于是「限制长边 1920」实际去限制**短边**。
   实测中 `landscape=true` 就是这条错判。

2. **预览对比窗会明显错位。** `main.ts:264-279` 把图片读成 base64 data URL，
   `PreviewApp.tsx:86-98` 用 `<img src={dataUrl}>` 渲染。现代浏览器对 `<img>` 默认应用 EXIF 方向，
   于是**「处理前」自动转了 90°，「处理后」已被剥离 EXIF 保持躺倒**
   → 同一个滑块对比视图里，左边竖着、右边横着，图像完全对不上。
   这是用户**一眼就能看到**的现象，比「导出后躺倒」更容易被发现。

修复仍是那一行，但顺序必须在 resize **之前**：

```ts
let pipeline = sharp(input.path, { failOnError: false, limitInputPixels: 268402689 })
  .rotate();   // 无参 = 按 EXIF 自动定向，顺带清掉标记，之后丢元数据也安全
```

另外 `FileScanner` 也应把 `metadata().orientation` 折算成视觉尺寸后再写入 `dimensions`，
否则 resize 的轴判断仍然是错的（`.rotate()` 只解决输出，不解决已落库的 dimensions）。

### P1-C 参数三处重复（未修，且这次查清了它为什么会「碰巧正确」）

参数仍是三份：`AppContext.state.processingParams`（真正加工用的）、
`ParameterPanel` 的 8 个 `useState`（UI 显示的）、`localStorage['batchpic_processing_settings']`（持久化）。

`ParameterPanel.tsx:92-121`：

```tsx
const currentParams: ProcessingParams = { ... };        // 每次渲染都是新对象
const debouncedParams = useDebounce(currentParams, 300);
useEffect(() => { onChange(debouncedParams); }, [debouncedParams]);
```

而 `useDebounce.ts:16-26` 的依赖是 `[value, delay]`。**每次渲染 `value` 都是新对象引用**，
于是计时器被反复清掉重建；fire 之后 `setDebouncedValue(新对象)` 又必然触发一次重渲染
→ **每 300ms 一次自我维持的全树重渲染空转，只要面板挂载就一直转**。
副作用：`state.processingParams` 每 300ms 换一次引用 → `MainWindow` 的
`autoProcessImages` / `handleFilesDropped` 两个 `useCallback` 跟着每 300ms 重建。

它之所以看起来没坏：`handleFilesDropped:167` 有一句 `setProcessingParams(DEFAULT_PARAMS)`，
但同一渲染周期里 `autoProcessImages` 闭包拿的是**滞后**的 `state.processingParams`（面板推上来的那份），
两者互相抵消。**代价**：启动后 300ms 内（面板还没把 localStorage 里的设置推上去）拖入第一批文件，
会用 `DEFAULT_PARAMS`（quality 70、无 resize、无 format）加工，而 UI 显示的是用户上次的设置。

## 2. 本次新发现

### N1（P1）参数持久化：一次把用户**全部**设置丢掉

`storage.ts` 的校验用的是**白名单**，而 UI 能产出白名单以外的值：

| 位置 | 可产生值 | 校验要求 | 结果 |
| --- | --- | --- | --- |
| 质量滑杆 `ParameterPanel.tsx:278` | `min=10 max=100` 任意整数（如 83） | `storage.ts:217` `[60,70,75,80,85,90]` | 不通过 |
| 目标大小输入 `:306,309` | `10..20480`（如 15000） | `storage.ts:225` `5..10000` | 不通过 |

`loadProcessingSettings:279-282` 遇到任何一个字段不合法就 `return null`
→ **整份设置回退默认**，不是只丢这一项。用户把质量拖到 83、重启应用，所有参数（尺寸、格式、元数据）一起被清空。

顺带：目标大小的约束在三个地方三套数（`constants.ts:62-66` MIN5/MAX10000、
面板 10/20480、`storage.ts` 5/10000），`DEFAULT_QUALITY_PRESET` 是 80 而
`AppContext.DEFAULT_PARAMS` 是 70。建议收敛成一份常量，UI 取值范围由它派生。

### N2（P1）targetSize 的中间态是「有损再压缩」

`ImageProcessor.ts:485`：

```ts
const inputBuffer = await pipeline.toBuffer();   // 不指定格式 → 按原格式默认参数编码
```

对这一层没设格式，JPEG 会按 sharp 默认质量（80）编码一次；随后 `:494` `sharp(inputBuffer)`
再解码、再按目标质量编码。**JPEG 在进入二分搜索之前就已经被压过一次**，
之后每一轮迭代都从这张受损的中间图开始 —— 既多了 CPU，也让最终画质低于目标质量应有的水平。
建议改为把 `pipeline` 的参数化结果固化成无损中间态（如 raw/PNG），或按轮次重建管线而不是先编码一次。

### N3（P1）PNG 的 quality 对体积几乎无效

**实测（同一份取证文件 [4]，噪声图避免纯色图被无损压扁）：**

```
q=  1 → 83.2KB   q= 30 → 89.2KB   q= 60 → 89.2KB   q= 80 → 89.2KB
q= 85 → 89.2KB   q= 90 → 89.2KB   q=100 → 89.2KB
```

q≥30 之后体积**完全饱和**，q=1 也只小 7%。上一版报告说的是「非单调」，本次结果是「单调但饱和」——
两次不一致本身就说明这个参数不可预测。两个后果：

1. smart 模式给 PNG 定 `quality: 85`（`constants.ts:32-36`）**等于没压**，只是顺手剥了元数据；
2. `compressToTargetSize` 的二分查找在饱和平台上无法区分质量档位，
   目标体积对 PNG 实际不可达（上一版实测：目标 50KB，产出 20.7KB，只有目标的 41%）。

建议：PNG 不参与 quality 二分，走 `compressionLevel: 9` + `palette`（可控）或尺寸优先策略，
达不到目标时明确回报「目标不可达」而不是静默兜底到 quality 1。

### N4（P2）打包产物里塞进了开发/无关依赖

`electron-builder.json5:20-24` 只列了 `dist/**`、`package.json`、`node_modules/sharp/**`，
但 electron-builder 会**自动带上 package.json 里的全部 production dependencies**。
实测解析 `release/win-unpacked/resources/app.asar` 的目录表（`asar-report.txt`，1876 个文件，构建于 **2026-07-17**）：

```
== runtime dependency probes ==
  PRESENT  node_modules/file-type      PRESENT  node_modules/p-limit
  PRESENT  node_modules/sharp          PRESENT  node_modules/lodash
  PRESENT  node_modules/react          PRESENT  node_modules/fast-check
```

- `lodash` + `@types/lodash`：`src/` **零引用**（grep 确认），却在 `dependencies` 里 → 打进了安装包；
- `fast-check`：纯测试库，在 `dependencies` 里 → 打进了安装包；
- `react` / `react-dom`：已被 Vite 打进 `dist/renderer`，又被整包复制一遍。

> 同时**纠正上一版报告 P2-10 的猜测**：`file-type` 与 `p-limit` 并**没有漏打包**，
> 二者都在 asar 里。打包链路是通的，问题是「多带」而不是「少带」。
>
> 另外 `release/` 产物构建于 2026-07-17，**早于 09-15 的修复提交**，属陈旧产物，
> 不要拿它当当前版本的验收依据。

### N5（P2）`validateOutputDirectorySafety` 在 Windows 上等于空转

`OutputManager.ts:17-60` 的黑名单是 POSIX 路径（`/etc`、`/usr`、`/bin` …），
判定方式为 `path.resolve(forbiddenDir)`。在 Windows 上 `path.resolve("/etc")` 得到的是
**当前盘符下的 `D:\etc`**，与系统目录毫无关系。这段「防止写入系统目录」的校验在本项目的目标平台
（`electron-builder.json5` 只配了 mac/win）上提供的是**虚假的安心感**。

### N6（P2）`ImageProcessor.test.ts` 的解析失败已定位到 `p-limit`

`processBatch` 相关的两条用例报 `Jest encountered an unexpected token`。
`ImageProcessor.ts:19` 是 `(await import("p-limit")).default`，而 **`p-limit@7` 是纯 ESM 包**，
落在 jest 默认的 `transformIgnorePatterns` 之外 → ts-jest 无法转换。
影响面很小（只有真正调用 `processBatch` 的两条用例），修法二选一：
`transformIgnorePatterns: ['/node_modules/(?!(p-limit|yocto-queue)/)']`，
或把 `p-limit` 降到提供 CJS 的版本。

### 7.2 为什么只拦「源目录」这一条路径

`getOutputPath` 实际产出两类路径，语义完全不同：

| 场景 | 目标位置 | 会不会吃掉用户既有文件 | 本次处理 |
| --- | --- | --- | --- |
| 换格式（`input.format !== format`） | **源目录**同名、只换扩展名 | **会**：撞上的可能是用户自己的图 | 默认拦截，可显式放行 |
| 同格式 → `{folder}-processed` / 指定 `outputRoot` | 应用自己的产物目录 | 不会（是我们自己上一轮写的） | 保持可覆盖 |

如果对第二类也加存在性探测，**重复导出会全部跳过**——第二次点导出时产物目录里已经全是上一轮的产物。
所以护栏必须按 `input.format !== format` 分流，这正是用户拍板的「只保护源目录」（§5 问题 1）。

### 7.3 顺带查清：`OutputManager.getOutputPath` 是死代码

§1 提到两份 `getOutputPath` 逐行重复。本次确认：

- 生产代码里**没有任何调用点**指向 `OutputManager.getOutputPath`
  （导出走 IPC → `main.ts` → `SharpImageProcessor.processBatch`）；
- 它只被 `OutputManager.test.ts` 覆盖。

因此护栏只加在真正生效的那一份。`OutputManager.getOutputPath` 的注释已改成如实描述，

### 7.4 两类冲突，两种拦截

`findExistingOutputBlocker` 除了探测磁盘，还维护一张**运行内的目标认领表**
（`claimedOutputs`，键按小写归一化）：

| 冲突类型 | 例子 | 处理 |
| --- | --- | --- |
| 与既有文件冲突 | 源目录已有 `logo.png`，现在要把 `logo.jpg` 转过去 | 默认跳过并保留原文件；勾选开关后替换 |
| 运行内互相覆盖 | 同时拖入 `logo.jpg` + `logo.png`，都转 `webp` | **无论开关如何**都跳过后者——开关只解决"与磁盘上既有文件"的关系，不解决"这一批里两张图抢同一输出" |
| 同一源文件重复出现 | 同一路径被拖入两次 | **不算冲突**，按认领表的 owner 判等放行 |
