# 换栈评估：Tauri 2 与 Wails v2（2026-09-28）

起因：Windows 产物过重（`win-unpacked` 278.9 MB，其中 **Chromium 运行时 251 MB / 90%**，
安装包 83.8 MB）。目标是在**尽量保留现有产品语义**的前提下把体积降一个数量级。

本文所有环境结论均来自本机实测，非文档推断。

---

## 摘要

| | 结论 |
| --- | --- |
| Wails v2 | **本机零安装成本即可开工**（Go 1.26.1 已装，`wails doctor` = SUCCESS） |
| Tauri 2 | **本机走不通官方路线**：缺 `link.exe`，且账户非管理员无法安装 VS Build Tools |
| 共同瓶颈 | 不是框架，是**图像处理栈的等价性**。sharp 的三个编码特性在纯 Go / 纯 Rust 生态均无等价实现 |
| 下一步 | 建议先做 Wails 外壳 spike 拿到真实体积数据；图像栈方案（下方①~④）需单独拍板 |

## 2. 三方对比

| 维度 | Electron（现状） | Wails v2 | Tauri 2 |
| --- | --- | --- | --- |
| 渲染内核 | 内置 Chromium 251 MB | 系统 WebView2 | 系统 WebView2 / WebKit |
| 后端语言 | Node + TS | Go | Rust |
| 预估安装包 | **83.8 MB**（实测） | 约 10–15 MB | 约 8–15 MB |
| 本机工具链门槛 | 已具备 | **≈ 0（已就绪）** | 高（缺 linker，且非管理员） |
| 前端复用 | — | ✅ 现有 React + vite 产物可直接复用 | ✅ 同 |
| IPC 改造 | — | Go struct 方法 → **自动生成** JS/TS 绑定 | 需手写 `#[tauri::command]` |

迁移面（代码规模实测）：

- `src/main` **2304 行** TS 需重写（含 13 个 `ipcMain` handler、22 个 preload API）
- `src/renderer` **2771 行** React —— **几乎不动**，只需把 `window.electronAPI` 换成一层适配
- `src/utils/storage.ts` 296 行需换持久化适配
- **`src` 下测试 16368 行** —— 与主进程耦合的部分是最大的隐性成本：迁 Go 要改写成 `go test`，
  迁 Rust 同理，所有涉及像素/文件大小的 golden 断言都需要重建

## 3. 真正的瓶颈：图像栈

`ImageProcessor.applyFormatWithQuality()` 依赖 sharp（libvips）的三个能力：

| sharp 用法 | 纯 Go | 纯 Rust |
| --- | --- | --- |
| `jpeg({ quality, mozjpeg: true, chromaSubsampling: '4:2:0' })` | ❌ std `image/jpeg` 非 mozjpeg，体积普遍大 5–10% | 需引入 mozjpeg 系 crate |
| `png({ quality, compressionLevel: 6, adaptiveFiltering: false })` | ❌ std `image/png` **没有 quality 概念、不做调色板量化** | 需引入 quant 系 crate |
| `webp({ quality, effort: 4 })` **有损** | ❌ `nativewebp` 仅支持 **VP8L 无损**，无 quality 参数 | 需引入 libwebp 系 crate |

连带影响：

1. **targetSize（压缩到目标大小）模式**依赖二分搜索反复调用上述三个编码器 ——
   编码器语义变了，**收敛结果跟着漂**。
2. 项目的核心卖点（批量导出后体积可控）正是建立在这些编码语义上；一旦语义漂移，
   就得**重建全部 golden 断言**，这部分工作量远大于「把 TS 翻成 Go」。
3. EXIF 自动定向、视觉尺寸算长边/短边等约定（`processors/exif.ts`）也要重新实现。

**结论：框架选择决定的是「能不能装起来」，图像栈决定的是「换完之后是不是同一个产品」。**

## 4. 四条路径

| # | 做法 | 体积 | 质量保真 | 代价 |
| --- | --- | --- | --- | --- |
| ① | Go/Rust + CGO 引 libwebp + mozjpeg + quant | ~20–25 MB | **最接近现状** | 需要 C 工具链（MinGW zip 261 MB，用户级可装，非管理员可做） |
| ② | 保留 Node + sharp 做 sidecar，Go/Rust 通过子进程调用 | ~50–70 MB | **完全一致** | 要打包 Node 运行时，收益缩水；进程管理复杂度上升 |
| ③ | 砍掉 WebP 输出，只留 JPEG/PNG | ~10–15 MB | 有损 classpath 部分语义仍漂 | 属**产品决策**，需业务确认 |
| ④ | 接受纯 Go/Rust 降级（webp 只能无损等） | ~10–15 MB | ❌ 体积可能翻倍 | 不推荐，会破坏「压缩到目标大小」卖点 |

## 5. 建议

1. **先做 Wails 外壳 spike**（预计 10 分钟）：`wails build` 出一个空壳，挂上现有 `dist/renderer`，
   拿到**真实的二进制体积数字**，验证"渲染层能否零改动复用"。工具链已就绪，成本极低。
2. **图像栈先用路径 ① 做一次垂直切片**：只验证 `jpeg quality 70` / `webp quality 70` 在
   Go 侧的输出与 sharp 的差异有多大 —— 这个数据出来之前，任何迁移工作量估算都是猜的。
3. 在拿到 1、2 的实测数据之前，**不要开始重写 `src/main` 的 2304 行**。
4. 若最终只想要快速减重：**先做无损瘦身（删 `locales/` + `app.asar` 冗余依赖，约 −43 MB）**，
   这是零风险、当天可见收益的选项，与换栈不冲突。

## 7. 结论（2026-09-28）：保持 Electron，不换栈

综合第 1~4 节的实测数据，用户决定**维持现状**。理由链条如下：

1. **收益上限被钉死在「减去 Chromium 251 MB」上**，而这是唯一真实存在的收益；
   安装包从 83.8 MB 降到约 10–15 MB 的前提，是要先跨过下面两条成本。
2. **工具链成本**：Tauri 在本机走不通官方路线（缺 `link.exe` + 非管理员），
   只能走官方不支持的 GNU 路径；Wails 虽然零成本，但这条优势不足以单独驱动迁移。
3. **真正的高墙是图像栈，且与框架无关**：sharp 的 mozjpeg / png 量化 / webp 有损
   在纯 Go、纯 Rust 生态里都没有等价实现。要保真就得引 C 库（回到工具链问题）或
   保留 Node+sharp sidecar（收益基本被吃回去）。不保真则会动摇
   **「压缩到目标大小」这个核心卖点**，并需要重建全部 golden 断言。
4. **迁移面**：`src/main` 2304 行重写、`src` 下 16368 行测试改写，
   外加 **147 条既有失败用例**要在新栈里重新判定基线 —— 这笔投入换来的主要是包体积，
   而非功能。

> 一句话：**换栈的成本是一次性的、确定的；收益是体积数字，
> 但它需要用产品语义的差异去交换。当前不值得。**

### 后续若仍要减重，走不换栈的路线（与本文互斥）

- **无损瘦身**：删 `locales/`（约 35 MB）+ 清 `app.asar` 内冗余依赖
  （`react-dom` 4.3 MB、`lodash` 1.34 MB 零引用、`fast-check` 0.8 MB 测试库，合计约 6.9 MB）
  → 约 **−43 MB**，不改任何业务行为。
- 其余（延迟加载、按需打包、Electron 版本升级自身携带的 Chromium 瘦身）均属同类低风险措施。
