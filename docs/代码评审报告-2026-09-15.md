## 2. P0 严重问题（依然存在）

### P0-2 移除元数据 + 不自动旋转 = 手机照片躺倒（本次实测复现）

`ImageProcessor.applyFormatWithQuality()` 只在保留元数据时调 `withMetadata()`，
**`process()` 主流程里 `sharp(input.path, ...)` 之后没有任何 `.rotate()` 调用**：

```ts
let pipeline = sharp(input.path, {
  failOnError: false,
  limitInputPixels: 268402689,
});
// ↑ 没有 .rotate() → EXIF Orientation 永远不会被"烧"进像素
```

而默认 `removeMetadata ?? true`，smart 模式强制 true → EXIF 的 Orientation 标记被剥掉、像素却没旋转。

**本次实测**（`test-temp-review/verify-now.mjs`，用项目自身的 sharp）：

```
== [1] EXIF 方向 ==
  源图            : 200x100 orientation=6
  当前 pipeline   : 200x100 orientation=undefined   <<< 与源图同尺寸=像素未旋转
  加 .rotate()    : 100x200 orientation=undefined   <<< 已烧进像素
  >> 结论：当前实现输出 200x100（躺倒），应为 100x200
```

最坑的是**预览是对的、导出是错的**：渲染进程用 `<img src="data:...">` 展示，
现代浏览器对 JPEG 会自动应用 EXIF 方向，用户对比窗里看着正常，导出的文件却是躺倒的。

修复（在 resize 之前加一行，注意顺序）：

```ts
let pipeline = sharp(input.path, { failOnError: false, limitInputPixels: 268402689 })
  .rotate();   // 无参数 = 按 EXIF 自动定向；且顺带清掉标记，之后丢弃元数据也安全
```

> 这一条是当前**最高优先级**：它直接影响用户拿到手的文件，且用户难以自查。

### P0-3 格式转换静默覆盖用户文件（本次实测复现）

`ImageProcessor.getOutputPath()`（`ImageProcessor.ts:676-695`）与
`OutputManager.getOutputPath()`（`OutputManager.ts:156-183`）**两份重复实现**，规则一致：

> 转换格式（jpg → png）时，写到**原文件所在目录**、同名、仅换扩展名；已存在的同名目标「被覆盖」。

**本次实测**（`test-temp-review/verify-now.mjs` [3]）——在文件夹里预置两张不同的 `logo.jpg` / `logo.png`：

```
  jpg->png 目标路径 : ...\Pictures\logo.png
  覆盖前 logo.png   : 158 bytes / mtime=2026-09-15T08:48:48.712Z
  覆盖后 logo.png   : 118 bytes / mtime=2026-09-15T08:48:48.721Z
  >> 既有文件被覆盖  : 是 <<< 静默覆盖，不可恢复
```

同时实测确认**两份实现的规则完全一致**（0 处漂移）：

```
== getOutputPath 结果（左=ImageProcessor，右=OutputManager）==
  [单文件 jpg -> png（换格式）]     两者均为 ...\Pictures\logo.png
  [单文件 jpg -> jpg（同格式）]     两者均为 ...\Pictures-processed\photo.jpg
  [文件夹拖入 jpg -> png（嵌套）]   两者均为 ...\Pictures\trip\sub\a.png
  [文件对话框单文件（无 sourceRoot）] 两者均为 C:\Users\ma\BatchPic-Output\solo.jpg
  >> 不一致用例数: 0
```

**注意**：这两份重复实现现在会**同步维护**（本次是两边同时改的），所以漂移风险是"暂时不存在"而非"结构上排除"。
真正的隐患是——两处都有 `input.format !== format` 的分支，**任何一次单边修改都会立刻造成行为分叉**，
而单测只覆盖 `OutputManager` 一份（`ImageProcessor` 那份没有任何直接测试）。

修复方向（需产品拍板，见 §5）：
1. 统一到一处实现（`OutputManager` 单一权威，`ImageProcessor` 委托注入），消除双份。
2. 写入前 `fs.access()` 探测同名文件：存在则按策略「加序号 / 跳过并计入失败 / 用户确认」，绝不静默覆盖。
3. `Overwrite original` 作为**显式选项**存在（这也是 `TODO.md` 原本的意图）。

### P0-4 输出目录策略跑偏：`Desktop-processed` 兄弟目录 + 「Open Folder」打开上级目录

`FileScanner.scan()` 对单个文件也传 `sourceRoot = path.dirname(inputPath)`；
`OutputManager.createOutputDirectory()` 于是做：

```ts

const outputPath = this.getOutputDirectoryForSource(sourceRoot);  // → C:\Users\ma\Desktop-processed
await fs.mkdir(outputPath, { recursive: true });
...
return this.getCommonParent([...sourceRoots]);      // ← 返回的是「父目录」，不是产物目录
```

`getCommonParent()` 单个元素时 `return path.dirname(paths[0])`，所以：

**本次实测**（`test-temp-review/verify-output-path.mjs`）：

```
== createOutputDirectory 返回值语义 ==
  单文件夹拖入时 sourceRoots 去重后: C:\Users\ma\Pictures-processed
  getCommonParent(...) => C:\Users\ma
  真实产物目录         => C:\Users\ma\Pictures-processed
  >> 「Open Folder」打开的是: C:\Users\ma（上级目录，非产物目录）
```

- 从桌面拖 1 张图 → 在桌面**旁边**创建 `Desktop-processed/` 兄弟目录（下载目录同理 → `Downloads-processed`）；

修复方向：`createOutputDirectory` 返回**实际产物根目录**；或改成 `OutputManager` 持有产物根列表，
UI 逐目录揭示。

### P0-5 「开始导出图片」被永久隐藏，手动导出路径不可达

`MainWindow.tsx:471`：

```tsx
{hasFiles && !(state.autoProcessOnDrop && state.result) && ( ...导出按钮... )}
```

而：
- `autoProcessOnDrop` 默认 `true`（`AppContext.tsx`）；
- 顶部那个自动处理开关**仍是注释状态**（`MainWindow.tsx:425-435` 整块被 `{/* ... */}` 包住），

## 3. P1 高价值问题

### 3.1 P1-A PNG 的 `quality` 不单调，`targetSize` 对 PNG 形同虚设（本次复现）

`applyFormatWithQuality()` 对 PNG 使用 `png({ quality, compressionLevel: 6, adaptiveFiltering: false })`。
sharp 里 PNG 的 `quality` 只在调色板量化路径下才有意义，**行为非单调**。

**本次实测**（噪声图，避免纯色图被无损压到几百字节而失去区分度）：

```
== [2] PNG size vs quality（按 applyFormatWithQuality 的参数）==
  q=  1 → 8.7KB
  q= 30 → 9.4KB
  q= 60 → 9.5KB
  q= 80 → 9.5KB
  q= 85 → 9.5KB
  q= 90 → 9.8KB
  q=100 → 10.2KB
  >> 是否单调递减: 否 <<< 二分查找前提不成立
```

> 注：首版报告里的 `q60=166KB / q100=21KB` 出现在更高熵的图上，方向相反；本次用噪声图得到的是
> **单调递增**。两次结果不一致本身就说明该参数行为不可预测——这正是问题所在。

后果：
1. `compressToTargetSize()` 用**二分查找**假设「质量越低文件越小」，前提对 PNG 不成立
   → 迭代在乱跳，最后可能落到「quality 1 兜底」分支并把结果直接写盘，target size 对 PNG 实际不可用；
2. smart 模式给 PNG 定的是 `quality: 85`，可能把 PNG **压得比原图更大**，与「智能压缩」的承诺相悖。

建议：PNG 不参与 quality 二分，改用 `compressionLevel: 9` + `palette: true`（可控）+ 必要时无损优化；
`compressToTargetSize` 对 PNG 走「尺寸优先」而非「质量优先」，无法达标时明确回报「目标不可达」。

### 3.2 P1-B 已恢复运行的 ImageProcessor 测试立刻报出 4 个真实问题

修好模块映射后，`ImageProcessor.test.ts` 从「0 执行」变为「4 failed / 29 total」，这 4 条值得逐条看：

| 用例 | 实际 | 期望 | 定性 |
| --- | --- | --- | --- |
| `should apply quality compression` | `361` | `< 343` | **真实缺陷**：100x100 小图用 quality 50 反而变大（JPEG 头开销），断言未考虑小图 |
| `should compress to target file size` | `20709` | `>= 43520` | **真实缺陷**：targetSize 模式产出 **20.7KB，只有目标 50KB 的 41%** —— 严重欠冲 |
| `processBatch should process multiple images with progress callback` | jest 解析失败 | — | 测试文件自身的 ESM 解析问题 |
| `processBatch should handle partial failures gracefully` | jest 解析失败 | — | 同上 |

第 2 条尤其关键：targetSize 的语义是「**压到目标体积以内**」，但产出只有目标的 41%，
说明二分收敛逻辑失真（对大图/小图的尺度判断有误），用户会拿到画质被过度牺牲的图。

第 1、2 条都是**首版评审没能看到的真实回归**——正因为套件之前根本没跑。

### 3.3 P1-C 参数状态三处重复，靠 debounce 时序碰巧正确

同一个「处理参数」存在三份：

| 位置 | 性质 |
| --- | --- |
| `AppContext.state.processingParams` | 加工时真正用的 |
| `ParameterPanel` 的 8 个 `useState` + `currentParams` | UI 显示的 |
| `localStorage['batchpic_processing_settings']` | 持久化 |

`ParameterPanel` 每次渲染都**新建** `currentParams` 对象，`useDebounce(currentParams, 300)` 的依赖每次渲染都变
→ 计时器不断重置 → 只在「300ms 内没有渲染」时才把面板状态推给上层。
同时 `MainWindow.handleFilesDropped()` 每次拖入都执行 `setProcessingParams(DEFAULT_PARAMS)`，
把用户设置重置掉；只是因为它随后调用的 `autoProcessImages` 拿的是**同一个闭包里滞后的 `state.processingParams`**，
两者互相抵消才看起来正常。

建议：单一数据源——`ParameterPanel` 改为受控组件；持久化放到 Context 的一个 `useEffect`；
删掉 `setProcessingParams(DEFAULT_PARAMS)`，改为「首次启动从 storage 初始化」。

### 3.4 P1-D 输出路径：文档与实现仍矛盾（本次未修）

`docs/TODO.md:62-70` 明确定的是：

```
默认：Save to: Same folder    Suffix: -opt
同时支持：Subfolder: optimized / Overwrite original
```

而实现是「换格式写回源目录同名覆盖 / 同格式写 `{folder}-processed` 兄弟目录」。
两者**都不吻合**：既没有 `-opt` 后缀，也没有把覆盖变成显式选项。

且本次改动把实现侧的规则**写进了注释和测试**（「与产品共同决定」），文档侧却一字未动
→ **下一次读 TODO.md 的人会照着旧设计去改代码**，这是最容易复发的一类技术债。

**必须二选一**（见 §5 问题 1）。

### 3.5 P1-E 无取消机制；targetSize 会放大 10 倍计算量

- `processBatch` / `process-images-with-progress` 没有任何 abort 通道，`isProcessing` 期间用户只能等；
  中途关闭窗口会留下半成品文件。
- `compressToTargetSize()` 把整图 `toBuffer()` 后**每轮迭代重新 `sharp(inputBuffer)` 全量解码**，
  最多 10 轮 → 单图 CPU/内存放大一个数量级。
- `sharp.cache({ memory: 50, files: 20, items: 100 })` + `concurrency = ceil(cores*0.75)` 在 100MP 级图片下并发风险偏高；
  `MAX_PIXELS = 100_000_000` 与 `limitInputPixels = 268_402_689` 两个阈值不一致，
  且前者会**静默覆盖**用户设置的 `params.resize`。

### 3.6 P1-F 追加拖入时进度列表被整体重置

`handleFilesDropped()` 在 `setInputFiles([...旧, ...新])` 之后调用 `initializeImageProgress(newFiles)`，
于是 `imageProgress` 只含新文件：

- 老文件状态从 success 退回 pending 外观；
- 统计口径错乱：`totalCount = inputFiles.length`（全部）而 `completedCount/successCount` 只统计新批次，
  标题会显示成「3 / 10」这种矛盾数字；
- `ProgressPanel` 的 `memo` 比较函数按**下标**比较 `imageProgress`，新旧批次长度相同且状态相同时会跳过渲染。

建议：`initializeImageProgress` 改为「按 filePath 合并」。

### 3.7 P1-G 死代码、重复实现与依赖冗余（本次未动）

## 4. P2 建议项

1. **`openOutputDirectory` 用 `exec` 拼路径**（`OutputManager.ts`）：
   `execAsync(\`explorer "${dirPath}"\`)`，路径只做了「非空字符串」校验 → 含 `"` 和 `&` 时可注入命令。
   应改用 `shell.openPath(dirPath)`（Electron 官方 API，同时避免 `explorer.exe` 非零退出码被误报失败）。
2. **不支持的格式被静默丢弃**：`FileScanner.processFile` 对非 jpg/png/webp 直接 `return null`。
   用户拖 100 张 iPhone HEIC 照片会一张都不出现且没有任何提示。建议先把「跳过 N 个不支持文件」透出到 UI。
3. **一处坏路径拖垮整批**：`FileScanner.validatePath` 在 `scan()` 里是 `throw`，
   且用 `filePath.includes("~")` 判断（`Backup~2024/` 这类合法目录会被误杀）。
   建议改为「单路径失败 → 跳过并记录」，用 `path.normalize` 后的段判断。
4. **生产环境调试日志残留**：`DropZone.handleDrop` 每次拖入打 7 条 `console.log`；
   `ImageProcessor` 大量 `[Performance]` 日志。建议收敛到一个 `debug` 开关。
5. **升级 Electron ≥32 的破坏性变更**：`DropZone.tsx` 依赖 `(file as any).path`，
   该字段在 Electron 32 已移除，需改为 `webUtils.getPathForFile(file)`。当前锁 `^28.2.3` 暂时安全。
6. **缺 CSP**：`index.html` / `preview.html` 无 `Content-Security-Policy`；
   开发态 `loadURL("http://localhost:3000")` 端口硬编码，与 `vite.config.ts` 各写一份。
7. **`.gitignore` 漏了测试产物**：只忽略了 `/test-temp-pbt` 与 `/release`，
   而 `test-temp-webp/`（44 个 webp）、`test-temp-png-quality/`（44 个 png）、`test-temp-script/`、
   `test-temp-review/`、`src/test-temp/` 都不在忽略列表里（`git status` 里全部是 `??`）。建议统一 `/test-temp*`。
8. **文档漂移**：`docs/技术债.md` 写 `build:main` 会执行 `tsc -p tsconfig.main.json && tsc -p tsconfig.preload.json`，
   实际 `package.json` 已改为 `tsc -p tsconfig.main.json` + esbuild 编译 preload。
9. **`src/renderer/types/electron.d.ts` 是 `src/main/types.ts` 的手工副本**，
   已出现字段漂移（`CompressionParams` 少了 `removeMetadata`）。建议直接从 main/types 导入复用。
10. **`electron-builder.json5` 的 `files` 只列了 `dist/**`、`package.json`、`node_modules/sharp/**`**，
    但 `file-type` 是 main 进程的运行时依赖 —— 建议显式列出运行时依赖并在打包后用 `asar list` 校验。

## 5. 需要产品拍板的两处矛盾（本次未自行决定）

### 问题 1：输出路径策略，以哪边为准？

- **实现侧**（已固化）：换格式 → 源目录同名 + 覆盖；同格式 → `{folder}-processed` 兄弟目录。
  `ImageProcessor` 与 `OutputManager` 注释均写「decided with product」，`OutputManager.test.ts` 有 4 个用例锁死该规则。
- **文档侧**（`docs/TODO.md:62-70`、`:81-83`）：`Save to: Same folder` + `Suffix: -opt`，
  另可选 `Subfolder: optimized` / `Overwrite original`。

**选项 A**：以实现为准 → 更新 `docs/TODO.md`，把那段旧设计标注为「已废弃，现状是…」。
**选项 B**：以文档为准 → 改实现，把覆盖变成显式选项 + 加 `-opt` 后缀（会改变用户可见行为，且需推翻 4 个新测试）。

> 注：无论选哪个，**当前「换格式静默覆盖既有同名文件」这一行为本身**（实测确认 158→118 bytes）
> 都建议加上存在性探测，至少避免不可逆丢失。这可以独立于 A/B 决策先做。

### 问题 2：配置/文档类测试（8 个文件）怎么处理？

现状：`build-system.*`、`script-system.*`、`package-system.*`、`documentation.test.ts` 合计约 55 条失败中的主体，
其中多条会**真执行 `npm run build` / `npm run package`**（单套件最长 218 秒，且 `build-system.test.ts`
的 `afterEach` 会 `fs.rm(仓库/test-temp, recursive)`）。

**选项 A（推荐）**：精简后保留 —— 删掉真跑 tsc/build/package 的慢用例与超时 hook，保留纯静态断言
（package.json 脚本存在、electron-builder 字段、文档章节存在），并修正文案/路径漂移。
**选项 B**：修好并全部保留 —— 逐条对齐现状并加大超时，`npm test` 维持数分钟且会真执行构建。
**选项 C**：整体删除这 8 个文件 —— 配置正确性改由 CI（`tsc --noEmit` + 一次打包 smoke）保证。
